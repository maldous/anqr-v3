# Agent capability routing

This guide governs optional maintenance assistance, not ANQR runtime dependencies.
Read the repository's [AGENTS.md](../AGENTS.md), [toolchain](toolchain.md) and
current task before selecting a capability. Current user directions, platform
permissions, applicable instruction precedence and narrower project holds still
apply. A skill, plugin, successful identity read or readable file does not grant
source, publication, provider, credential or production authority.

## Establish the actual environment

For each executing environment, record the repository and commit/tree, task and
owned paths, applicable instruction files, tool and skill source/version or
content digest, invocation route, and the exact verification result. Keep this
operational evidence with the existing project issue or handoff. Do not copy
another host's absolute paths or assume its installed tools or signed-in
accounts are present here.

Distinguish these observations:

- **Readable:** the applicable instructions or skill file can be opened.
- **Discoverable:** this caller's actual catalog or supported discovery lists it.
- **Executable:** the intended binary or command ran successfully here.
- **Authenticated:** the selected connector or CLI verified the intended account.
- **Authorized:** the current task permits the specific operation and destination.

None of the first four observations implies the fifth. Record missing
capabilities precisely and continue independent permitted work; an optional
tooling gap is not a new universal product or release gate.

## Current product and presentation boundary

The accepted source at
`af6a23dd735a9cc92c29dd8db496e04aaaf73003` contains capability modules, an
in-process artifact package, repository/package guides and static QR validation
evidence. It has no application UI source, hosting configuration, mobile
packaging/store manifest, or build/start/deploy command. Future revisions must
recheck that boundary rather than treating this observation as permanent.

For this edition, Impeccable's applicable presentation scope is **Read-mode
documentation** and any separately selected existing demonstration surface.
Do not invent a web/mobile application, publish to the legacy public site, or
change QR artifact semantics to demonstrate a design tool. Record absent or
unavailable rendering/device coverage honestly.

The artifact package is not a hosted HTTP endpoint, MCP server or separately
published npm package. Source tests, internal grid decoding and static design
checks are not whole-product, camera, browser, service or production acceptance.

## Recovery and publication

Use a clean task-specific checkout at the selected accepted source. Preserve
dirty, stale, historical and other-owned checkouts; do not repair them as a
side effect. Verify installed dependencies against the lock before reuse.
An isolated locked bootstrap may restore the task's development environment
without replacing accepted product-test evidence or changing the global host.

Keep instruction changes distinct from actual adoption. Record the exact
candidate diff, relevant changed-path checks and an author-distinct review.
Retain the established integration publisher and current claims. Do not unpause
native admission, transfer a claim, replay a sealed effect, deploy, create
credentials or broaden permissions to prove that a guide works.

[Post-reboot environment verification and open gaps](https://linear.app/maldous/issue/UIF-265)
and [release destination inventory](https://linear.app/maldous/issue/UIF-270)
retain the actual observations and receipts. These issues are evidence
locations, not additional product-runtime dependencies.

The [documentation inventory and disposition map](documentation-map.md) records
the inspected canonical documents, source/API coverage and genuine remaining
gaps at its pinned revision. Refresh affected dispositions when source changes;
the map is not a substitute for the task's current evidence or instructions.
